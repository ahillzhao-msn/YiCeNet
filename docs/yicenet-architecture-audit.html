1. 核心逻辑与代码封装 C — 多处违反 SRP

组件行数职责评价
yicenet_engine.py 723 predict + attend + switch + chain signals + registry + checkpoint ❌ 7 个职责挤在一个类。predict() 237 行处理 tokenizer → env → routing → candidates → prescription
model.py ~300 YiCeNet.forward() + encode_context + evaluate_candidates + decode_action ⚠ forward() 返回扁平 dict (12+ keys)。无 typed result object
config.py 325 YiCeNetConfig + 路径解析 + 用户配置加载 ⚠ YiCeNetConfig 混含模型架构(hidden_dim)、训练(batch_size)、路径(data_dir) 三组独立参数
bootstrap.py ~920 env检测 + pip安装 + checkpoint下载 + tokenizer下载 + Hermes注册 + MCP注册 + cron + cleanup ❌ ~15 个职责挤在一个文件。跨平台逻辑未分离

hexagram.py ~80 generate_candidates() + 错综互变计算 ✅ 纯函数，无状态，无外部依赖 (仅 numpy)

2. 核心组件内部交互的接口定义 C — 隐性契约为主，显式接口不足

接口类型清晰度问题
predict(text, τ, deterministic, session_id, ...) → dict 无类型 dict 弱 返回值是扁平 dict，12+ key 无文档契约。调用者必须猜测 key 的存在性（selected_hexagram_name vs hexagram_name）
format_prediction(result, mode) → str 无类型 dict 入参 中 result 参数应为 TypedDict 而非 dict。当前隐式依赖特定 key 存在
MemoryBank.store_turn(session_id, turn_id, encoder_output, hexagram_id, summary) 无类型 中 encoder_output 是 numpy array 还是 list？无类型提示。session_id="" → skip prescription 是隐性行为
YiCeNet.forward() → dict 无类型 dict 弱 返回 dict 含 h, hexagram_idx, hexagram_probs, best_candidate_idx, candidate_idxs, candidate_values, action_ids, action_logits, probes, router_logits。无契约文档
CrossAttention.compute(query, keys) → weights numpy ndarray 强 query:(384,) keys:(N,384) → weights:(N,) float64。计算图清晰
ContextPrescription.generate() → Prescription dataclass ✅ 强 正确使用 Typed 返回 — retain_turns:list, summarize_turns:list, discard_turns:list, mode:str, attention_entropy:float, compression_ratio:float, key_insight:str
DataSource.scan_since(timestamp) → list[Sample] ABC + dataclass ✅ 强 cleanest 接口设计。Sample dataclass + abstractmethod + 3 实现
关键问题：隐性接口契约
predict() 返回 dict 时，调用方需假设 hexagram_id ∈ [0,63]，selected_hexagram_id 优先于 hexagram_id，
q_values 长度与 candidates 一致。但这些契约只有运行时测试保证，无编译时检查。

3. 逻辑耦合程度 C — 控制器式耦合，无依赖注入

高耦合模式

1. 控制器模式 (God Class)
yicenet_engine.py predict() 直接调用：
• tokenizer.encode()
• model.forward() / model.encode_context()
• build_env_vec()
• get_memory_bank()
• CrossAttention.compute()
• ContextPrescription.generate()
• compute_env_confidence()
• check_for_switch()
→ 7+ 硬编码依赖，无接口隔离
2. 硬编码实例化
yicenet_engine.py: self._model = YiCeNet()
model.py: self.encoder = TinyEncoder()
model.py: self.router = GumbelRouter()
model.py: self.value_net = ValueNetwork()
全部在 __init__() 中 new，不可替换。若要 mock value_net 测试，需子类化 YiCeNet

✅ hexagram.py
generate_candidates(hx_idx, attn_w) → (B,8)

✅ datasource/ 三层

flywheel 通过 scan_all_sources() 多态调用，不感知具体实现。

4. 接口边界与抽象隔离 C — 有边界但缺抽象层

边界类型状态说明
tokenizer.py 对外接口 函数级 ✅ 清晰 encode(text)→(tensor,tensor)。外部无需知道 Qwen/BPE/vocab 细节
hexagram.py 对外接口 函数级 ✅ 清晰 generate_candidates(hx)→(B,8)。纯数学逻辑
display.py 对外接口 函数级 ⚠ 弱 入参 result 是裸 dict，可以用 TypedDict 加固
MemoryBank → engine 单例 ❌ 缺隔离 全局单例，任何模块可 get_memory_bank() 并修改。测试时无法 mock
config.py 路径函数 全局函数 ❌ 缺隔离 yicenet_home()/data_dir()/checkpoint_dir() 全部是全局函数。测试需要修改 YICENET_HOME 环境变量
datasource/ ABC ✅ 最佳 DataSource ABC + 3 implements。flywheel 用多态调用
hermes_tool vs mcp_server 重复 ❌ 代码重复 两个文件各有自己的 _get_engine()，95% 相同的 registry 发现 + 懒加载逻辑
接口边界缺失最严重的问题
1. YiCeNetEngine 直接调 tokenizer.encode() → 无法替换 tokenizer
2. MemoryBank 是全局单例 → 测试无法隔离
3. yicenet_home() 是全局函数 + 环境变量 → 测试间可能污染
4. hermes_tool.py / mcp_server.py 重复 _get_engine() → 修一个漏一个

5. 外部交互接口 B — 清晰简约，但有重复

系统接口形式评价
Hermes 插件 hermes_tool.py: yicenet_predict(task_brief, τ, deterministic) → JSON str 函数（注册为 Hermes tool） ✅ 清晰。参数扁平，无嵌套
Claude Code (MCP) mcp_server.py: yicenet_predict(task_brief, session_id, τ, deterministic, environment) → dict FastMCP tool ✅ 清晰。比 Hermes tool 多了 session_id 和 environment
Hermes Plugin (hooks) pre_llm_call / post_tool_call / post_llm_call hooks 插件 hook 回调 ✅ 设计合理的生命周期 hook 模式
Python API YiCeNetEngine().predict(text, τ, deterministic, session_id, return_prescription, environment) → dict 类方法 ⚠ 7 个参数略多。return_prescription 是副作用标志位（应该拆成两个方法）
飞轮数据录入 submit_trajectory(data) → push to buffer 函数 ✅ 通用 Producer 接口。任意外部系统可调用
重复问题：hermes_tool.py vs mcp_server.py
两个文件各维护自己的 engine 懒加载 + registry 发现逻辑。
12 行几乎完全相同的代码。未来的任何第三方集成（比如 VSCode extension）将产生第三份副本。
→ 解决方案：将 _get_engine() + registry 发现提取到 yicenet_engine.py 或独立的 engine_provider.py

6. 抽象+继承/扩展模式 D — 严重不足

模式现状影响
ABC/Protocol仅 1 处 (ProbeExtractor in interfaces.py)无法替换各组件实现。测试必须用真实模型
依赖注入零。所有组件自 new无法 mock tokenizer / model / memory_bank
工厂模式部分: YiCeNet.from_pretrained(path)仅 model 有工厂。其他组件没有
策略模式无router 策略、candidate 生成策略不可替换
提供者模式无tokenizer / encoder 是硬编码的单一实现
DataSource 模式 (正确的示范)✅ ABC + 3 implementsflywheel 不感知数据来源。新增平台只需新增 DataSource 子类
缺乏扩展模式的直接后果
• 如果用户想用 SentencePiece tokenizer 替换 Qwen BPE → 必须修改 yicenet_engine.py
• 如果用户想用 1024-dim encoder 替换 256-dim → 必须修改 model.py 的骨架
• 如果用户想对 MemoryBank 做限流/持久化 → 必须修改 MemoryBank 本身
• 单元测试启动需要 22MB checkpoint + tokenizer + full model

7. 不同系统的交互隔离 B — 适中，个别缺陷

系统对隔离方式评价
Hermes ↔ YiCeNet hermes_tool.py 封装调用，不引入 Hermes 包 ✅ 干净。Hermes 通过插件 hooks 驱动，YiCeNet 无 Hermes 反向依赖
Claude Code ↔ YiCeNet MCP stdio 子进程 ⚠ 冷启动 26s，MCP 协议本身复杂。建议换 PreMessageSend hook
LOOM ↔ YiCeNet format_prediction(mode=) API 调用 ✅ 已清理。LOOM 不读 YiCeNet config，YiCeNet 无 LOOM 引用
飞轮训练 ↔ 数据源 DataSource ABC 多态 ✅ 最佳实践。新增平台 → 新增 DataSource 子类
bootstrap.py 同一文件处理所有平台 ❌ 跨平台逻辑未隔离。platform.system() 判断散落在 ~100 处

8. 工具类 / 配置类 / 数据类的系统层可见与共享 B — 适度共享，有散落

类别现状评价
配置 (config.py) yicenet_home() / get_config() 被 8 个模块使用 ✅ 适当共享。路径函数 + config 模板是正确的位置
模型参数 (YiCeNetConfig) 混含 model_arch + training + paths ⚠ 应拆为 ModelConfig / TrainingConfig / PathConfig 三个 dataclass
数据类 (dataclass) Prescription (cross_attn), TurnRecord (memory_bank), Sample (datasource) ⚠ 散落在各模块中。跨模块复用需要 import 具体模块
PrecomputedTables constants.py 中的全局单例 ⚠ 单例 + 全局。63×64 矩阵计算 1 次缓存没问题，但模式不统一
metrics MetricsLogger 单例 ⚠ 又是单例。3 种单例模式不一致（MemoryBank/constants/metrics 各有自己的单例实现）
公共类型 无 types.py / datatypes.py ❌ 如果 Hermes tool 需要 Prescription 类型，必须 from cross_attention import Prescription — 逻辑级 import
共享问题总结
• ✅ 好的共享：config.py 的路径函数、display.py 的格式化函数 — 正确放在顶层
• ⚠ 中等的共享：YiCeNetConfig 包含三组职责，但各模块只读需要的子集
• ❌ 不好的共享：无 types.py — Sample 在 datasource/__init__.py，Prescription 在 cross_attention.py，
TurnRecord 在 memory_bank.py。跨模块共享这些类型需要 import 逻辑模块

📊 综合评分与改进优先级

维度分数核心问题改进优先级
1. 核心封装 C predict() 237 行，bootstrap.py 920 行，YiCeNetConfig 3 职责 P0 — 拆分 predict() 和 YiCeNetConfig
2. 内部接口 C 无 TypedDict/类型契约，隐性传参 P1 — predict() 返回 TypedDict
3. 逻辑耦合 C God Class + 硬编码 new + 8 个全局单例 P0 — 引入 DI + IEngine/IModel/ITokenizer ABC
4. 接口边界 C MemoryBank 无 interface，hermes_tool/mcp 代码重复 P1 — 合并 _get_engine(), MemoryBank 加 IMemoryBank
5. 外部接口 B predict 参数略多，return_prescription 是副作用标志 P2 — 拆分 predict()/prescribe()
6. 扩展模式 D 仅 1 ABC，零 DI，零策略模式 P0 — 核心接口注入式重构
7. 跨系统隔离 B bootstrap.py 未隔离平台逻辑 P2 — 拆 bootstrap 为平台模块
8. 共享模式 B 无 types.py，config 三职责 P1 — 提取 types.py, 拆分 YiCeNetConfig
总分 C+ "局部干净，整体控制器" — 最好的部分是 DataSource 模式和 hexagram.py，最差的是预测流程的 7 合一控制器
重构路线图：从 data source 范式推广到全系统
核心思想：DataSource ABC 是最成功的抽象模式。将同一模式推广到所有核心组件：

① ITokenizer.encode(text) → ids,mask (当前: 硬编码 Qwen)
② IEncoder.encode(input_ids, mask) → h (当前: 硬编码 TinyEncoder)
③ IRouter.divine(h, τ) → idx,probs (当前: 硬编码 GumbelRouter)
④ IValueNetwork.score(embeds) → values (当前: 硬编码 3-layer MLP)
⑤ IMemoryBank.store/get(key) → records (当前: 全局单例)
⑥ IEngine.predict(text) → result (当前: YiCeNetEngine 单类)
